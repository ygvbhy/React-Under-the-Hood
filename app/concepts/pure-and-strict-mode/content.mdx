앱을 `<StrictMode>`로 감싸면 개발 중에 컴포넌트 안의 로그가 두 번씩 찍힙니다. 이 글은 React가 왜 컴포넌트를 두 번 호출하는지를, React가 컴포넌트를 순수 함수로 가정한다는 점과 함께 실행 결과로 확인합니다. 두 번 호출해도 결과가 같은 컴포넌트와 결과가 달라지는 컴포넌트를 나란히 비교합니다.

컴포넌트가 함수라는 것은 <JsLink slug="function-calls">함수 호출</JsLink>을 전제합니다. 예제 1·2의 컴포넌트는 자기 바깥에 선언된 변수를 읽고 바꾸는데, 함수가 바깥 변수를 찾는 방식은 <JsLink slug="scope-chain" anchor="이름을-찾는-순서">스코프 체인</JsLink>에서 본 것과 같습니다.

## 동작 원리

React는 모든 컴포넌트가 순수 함수(pure function)라고 가정합니다. 순수한 컴포넌트는 두 가지를 지킵니다.

- **같은 입력이면 같은 결과**: props와 state가 같으면 언제, 몇 번 호출해도 같은 JSX를 돌려줍니다. 여기서 같은 JSX는 같은 객체라는 뜻이 아니라 같은 화면을 나타내는 결과라는 뜻입니다. element와 그 안의 이벤트 핸들러 함수는 호출할 때마다 새로 만들어집니다.
- **렌더 전부터 있던 값을 바꾸지 않음**: 컴포넌트 바깥에 선언된 변수나 객체, 받은 props를 렌더 중에 바꾸지 않습니다. 렌더 중에 새로 만든 변수나 배열을 바꾸는 것은 괜찮습니다. React 문서는 이를 지역 변경(local mutation)이라고 부릅니다.

화면을 갱신하거나 애니메이션을 시작하거나 데이터를 바꾸는 것처럼, JSX를 계산해 돌려주는 일 외에 일어나는 변화를 부수 효과(side effect)라고 합니다. React 문서는 이런 변화가 렌더 중이 아니라 그 곁에서 일어나는 일이라고 설명합니다. 부수 효과는 보통 이벤트 핸들러에 둡니다. 이벤트 핸들러는 렌더 중에 실행되지 않으므로 순수할 필요가 없습니다. 렌더 중에 DOM을 읽거나 바꾸는 것도 같은 이유로 순수한 컴포넌트에서는 하지 않습니다. DOM을 바꾸면 렌더 전부터 있던 것을 바꾸게 되고, DOM을 읽어 결과를 정하면 결과가 props와 state가 아닌 것에 기대게 됩니다.

StrictMode는 이 가정을 어긴 컴포넌트를 개발 중에 찾도록 돕습니다. `<StrictMode>` 안의 컴포넌트에 대해 React는 순수해야 하는 함수를 개발 중에 두 번 호출합니다.

- 컴포넌트 함수 본문(최상위 코드만이며, 이벤트 핸들러 안의 코드는 포함하지 않음)
- `useState`, `set` 함수, `useMemo`, `useReducer`에 넘긴 함수

순수한 함수라면 두 번 호출해도 결과가 같으므로 아무 문제가 없습니다. 순수하지 않은 함수라면 두 번째 호출의 결과가 첫 번째와 달라질 수 있고, 그러면 숨어 있던 버그가 화면에 드러납니다. 이 두 번 호출은 개발 중에만 일어나고 프로덕션 빌드에서는 일어나지 않습니다.

그렇다고 프로덕션에서는 순수하지 않아도 괜찮은 것은 아닙니다. React 문서는 렌더가 언제든 일어날 수 있으므로 컴포넌트가 서로의 렌더 순서에 기대면 안 된다고 설명합니다. 또 컴포넌트가 순수하면 입력이 바뀌지 않은 컴포넌트의 렌더를 건너뛰어 성능을 높일 수 있고, 깊은 트리를 렌더하는 도중 데이터가 바뀌면 React가 낡은 렌더를 끝까지 마치지 않고 렌더를 다시 시작할 수 있다고 설명합니다. 이 건너뛰기는 기본 동작이 아니라 `memo` 같은 API로 직접 요청하는 최적화입니다. 기본으로는 다시 렌더하는 컴포넌트가 돌려준 JSX 안의 컴포넌트도 이어서 호출합니다("렌더링은 컴포넌트 함수를 호출하는 것" 개념). 즉 프로덕션에서도 컴포넌트가 몇 번 호출될지는 코드가 정할 수 없습니다. 호출 횟수에 기대는 컴포넌트는 그 자체로 틀린 코드이고, StrictMode의 두 번 호출은 그런 코드를 개발 중에 미리 드러내는 장치입니다.

  바꾸도록 쓴 코드입니다.
</Callout>

첫 렌더에서는 `Counter 본문`이 두 번, `useState`에 넘긴 `초기값 함수`도 두 번 찍힙니다. 이 실행(React 19.3.1)에서는 `Counter 본문` → `초기값 함수` → `초기값 함수` → `Counter 본문` 순서로 찍혔습니다. 이 순서는 react.dev가 정하지 않으며 버전에 따라 다를 수 있습니다. 버튼을 누르면 `클릭 핸들러`는 한 번만 찍힙니다. 이벤트 핸들러는 렌더 중에 실행되지 않으므로 순수할 필요가 없고, StrictMode도 두 번 호출하지 않습니다. 이어서 다시 렌더하면서 `Counter 본문`이 두 번 찍힙니다. 초기값 함수는 이번에는 찍히지 않습니다. `useState`의 초기값은 첫 렌더에만 쓰이기 때문입니다.

<Callout type="react18">
  React 18에서는 StrictMode가 두 번 렌더할 때 두 번째 렌더가 첫 렌더의 <code>{'useMemo'}</code>,{' '}
  <code>{'useCallback'}</code> 결과를 다시 쓰지 않았고(useMemo는 계산 함수를 다시 실행했습니다),
  처음 마운트할 때 ref 콜백을 한 번 더 실행하지 않았습니다. React 19부터는 두 번째 렌더가 이 두 훅에
  대해 첫 렌더의 결과를 다시 쓰고, 처음 마운트할 때 ref 콜백을 한 번 더 실행합니다. 근거는 이 두
  가지를 React 19의 변경으로 적은 [React 19 업그레이드
  가이드](https://react.dev/blog/2024/04/25/react-19-upgrade-guide#strict-mode-improvements)입니다.
  이 페이지의 예제에는 이 API들이 없습니다. 위 목록처럼 useMemo에 넘긴 함수도 두 번 호출 대상인데,
  이것과 결과 재사용이 함께 어떻게 동작하는지는 "memo·useMemo·useCallback" 개념에서, ref 콜백은
  "ref" 개념에서 다룹니다.
</Callout>

## 결과와 이유

StrictMode는 순수하지 않은 컴포넌트를 고쳐 주지 않고, 이 예제들처럼 두 호출의 결과가 달라도 경고하지 않았습니다. 순수해야 하는 함수를 개발 중에 두 번 호출할 뿐입니다. 순수한 컴포넌트는 두 번 호출해도 결과가 같고, 예제 2처럼 결과가 호출 횟수에 달린 컴포넌트는 두 번째 호출에서 결과가 달라져 화면에서 문제가 드러납니다.

<Callout type="misconception" title="StrictMode가 버그를 만든다">
  예제 1과 예제 2의 `Ticket`은 같은 코드입니다. 예제 1에서 화면이 1, 2, 3으로 보인 것은 버그가
  없어서가 아니라 한 번씩만 호출되어 드러나지 않았기 때문입니다. StrictMode는 결과가 호출 횟수에

  컴포넌트를 몇 번 호출할지는 코드가 정할 수 없으므로, 예제 1의 `Ticket`은 StrictMode가 없어도 틀린
  코드입니다.
</Callout>
